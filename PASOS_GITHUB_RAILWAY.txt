LEER ANTES DE SUBIR. Esta es una migracion de piloto, NO un despliegue garantizado de 50 llamadas simultaneas. Haz backup/commit de la version funcional. No publiques claves en GitHub.

ESTRUCTURA: web/, relay/, prompts/, tests/. Dos servicios Railway, NO cuatro.

1. Descomprime el ZIP y sube las cuatro carpetas a una RAMA DE PRUEBA de GitHub. No borres main.py ni Procfile de la raiz todavia. No subas claves. La carpeta prompts/ contiene plantillas de referencia: modificar un TXT no modifica la voz en ejecucion; saludo/voz por negocio vienen de Airtable, estilo general esta en relay/main.py.
2. Copia AIRTABLE_AI_PROMPT.txt en la IA de Airtable; aprueba el plan, no borres tablas. Deja negocio y numero en Borrador mientras pruebas el esquema. Revisa permisos del token para leer Negocios y Numeros y escribir Reservas y Conversaciones.
3. En un ENTORNO DE ENSAYO Railway conecta la rama de prueba: servicio web Settings > Root Directory /web, Start Command gunicorn main:app --bind 0.0.0.0:$PORT --workers 2 --timeout 120. Servicio voice-relay Root Directory /relay, Start Command uvicorn main:app --host 0.0.0.0 --port $PORT --workers 1. Genera dominios nuevos para ensayo y apunta CORE_BASE_URL y RELAY_VOICE_URL entre ellos. No cambies Twilio productivo para probar codigo incompleto.
4. Variables web existentes: AIRTABLE_TOKEN, AIRTABLE_BASE_ID, AIRTABLE_RESTAURANTS_TABLE=Restaurantes, AIRTABLE_CONVERSATIONS_TABLE=Conversaciones, OPENAI_API_KEY, OPENAI_MODEL, TWILIO_PHONE, INTERNAL_API_KEY, RELAY_VOICE_URL, DEFAULT_TIMEZONE. Nuevas: AIRTABLE_BUSINESSES_TABLE=Negocios, AIRTABLE_NUMBERS_TABLE=Numeros, TENANT_LOOKUP_MODE=legacy. En relay existentes: CORE_BASE_URL, INTERNAL_API_KEY, RELAY_PUBLIC_URL, RELAY_WS_URL, OPENAI_API_KEY, OPENAI_MODEL, TWILIO_AUTH_TOKEN, TTS_PROVIDER, TTS_VOICE, TTS_LANGUAGE, TRANSCRIPTION_PROVIDER, SPEECH_MODEL, SPEECH_TIMEOUT_MS, AIRTABLE_TOKEN, AIRTABLE_BASE_ID, AIRTABLE_RESERVATIONS_TABLE. Nueva: TENANT_LOOKUP_MODE=legacy. Las claves deben ser privadas y coincidir donde corresponde. No agregues la clave antigua publicada en el chat.
5. Ejecuta tests/test_smoke.py en entorno con dependencias de ambos servicios. Comprueba /health de ambos y una llamada de prueba al entorno de ensayo. En web pasa a shadow y deja relay en legacy; verifica comparacion. Solo tras activar Negocio y Numero en Airtable y revisar los datos, pasa ambos a new y prueba Voice, WhatsApp, reservas y un segundo negocio ficticio. Cambiar variable Railway reinicia/despliega; agregar un negocio a Airtable en modo new NO requiere deploy.
6. Para produccion cambia Root Directory del servicio web a /web SOLO cuando la nueva version haya pasado pruebas. Relay ya usa /relay. Cambia web primero en ventana controlada, verifica /health, luego relay. Mantén copia del commit anterior y configuracion Root Directory anterior para revertir. Un despliegue puede afectar WebSockets activos: no prometas continuidad sin probarla.
7. No uses este piloto con seguros reales: no hay autenticacion del asegurado ni busqueda segura de PDFs. VERIFY_TWILIO_SIGNATURE debe validarse y probarse antes de produccion; dejar false es solo diagnostico. El codigo no incluye Stripe porque el ultimo main.py aportado tampoco lo tenia; no sustituyas produccion si dependes de /stripe-webhook.
8. Capacidad: Airtable tiene limites API; el piloto hace varias consultas por llamada y no garantiza 50 simultaneas. Para escala: base indexada/caché, limites del proveedor, pruebas de carga, idempotencia transaccional de reservas, y verificacion de firmas en todos los webhooks.
